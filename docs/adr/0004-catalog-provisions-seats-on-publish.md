# ADR 0004: Catalog provisions seats when an event is published

Status: Accepted — 22 November 2026 (team meeting).

## Context

FR-011 originally let admins create, update and delete seats through Inventory. The team decided that admins should not manage seats directly. Seats and their prices are generated by the system, and Inventory only tracks seat availability and holds.

## Decision

- When an admin publishes an event, Catalog generates its seats: a random whole number from 70 to 100, in section `GENERAL`, each with a random price of 100 to 1000 currency units stored as `priceCents`. The generator is seeded from the event id, so a retry produces identical seats.
- Catalog sends the seats to Inventory through the internal route `POST /internal/events/{eventId}/seats`. Inventory stores them as `AVAILABLE` in one transaction and ignores the call if the event already has seats.
- Catalog changes the event status to `PUBLISHED` only after Inventory confirms. If Inventory is unavailable or rejects the request, publish returns `503` and the event stays `DRAFT`.
- Before opening a hold, Inventory checks through `GET /api/events/{eventId}` that the event is published.
- The admin seat create, update and delete routes in Inventory are removed. This supersedes the original FR-011.

## Consequences

- Catalog and Inventory now depend on each other synchronously. Each call needs bounded timeouts and a clear `503` when the other service is down.
- Draft events have no seats, so deleting a draft cannot orphan seats. If seats were stored but the status change failed, the event stays `DRAFT`; retrying publish is a no-op for Inventory and the seats are harmless until the event is published.
- The Catalog call sits before the hold transaction in Inventory, so it does not extend database locks, but a slow Catalog can slow hold requests.
- Prices are generated, so admins cannot set or change them in the MVP.
- Catalog never writes to Inventory's database; it uses Inventory's API, which keeps ADR 0002 intact.
