# inventory-service

Owns event seats, seat holds, availability, hold confirmation/release, and authoritative hold expiry. It stores `event_id` and `booking_id` as external UUID references; it does not own Event or Booking entities. Seats are generated by Catalog when an event is published and provisioned through an internal endpoint; admins do not create, update or delete seats through Inventory.
## Local run

From repository root:

```bash
docker compose up -d inventory-db
cd inventory-service
mvn spring-boot:run
```

Health: http://localhost:8082/actuator/health

## Tables and entities

- `event_seat` → `Seat.java`, `SeatStatus.java` (existing skeleton / V1 migration).
- `seat_hold` → `SeatHold.java`, `HoldStatus.java` (approved V2 schema baseline).

`SeatHold.expiresAt` in Inventory is the authoritative expiry. The default hold duration is 10 minutes. A partial unique index permits at most one `ACTIVE` hold per seat. Multi-seat holds must be all-or-nothing in one local transaction.

## Seat provisioning and event check (planned)

Seats are not created by admins through Inventory. Catalog generates them when an event is published and sends them to `POST /internal/events/{eventId}/seats` (Catalog service only).

- Inventory creates all seats in one transaction as `AVAILABLE`.
- If the event already has seats, nothing changes and the call succeeds, so retrying publish is safe.
- Invalid input (empty list, duplicate labels, negative price) returns `400`.

Before opening a hold, Inventory asks Catalog (`GET /api/events/{eventId}`) whether the event is published. A missing or unpublished event is rejected, and an unavailable Catalog returns `503`. The call happens before the hold transaction starts and uses bounded timeouts, so it does not extend database locks.

## Booking integration contract

Inventory remains the owner of seat availability and seat state transitions. Booking does not
create or update seat records directly.

The Booking workflow is:

1. Booking sends the event ID and selected seat IDs to Inventory.
2. Inventory returns one status for each requested seat.
3. If all seats are `AVAILABLE`, Booking requests an atomic hold with an expiry time.
4. Inventory returns a hold ID and the authoritative expiry time.
5. After simulated payment succeeds, Booking asks Inventory to confirm the hold; seats become `SOLD`.
6. If payment fails or an unpaid booking is cancelled, Booking asks Inventory to release the hold.

The hold ID is stored by Booking only as an external reference. Booking does not create an
Inventory entity or a cross-service JPA relationship. The local Booking development stub
simulates these calls until the Inventory REST service is available.
